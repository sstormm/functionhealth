Each step is a coherent unit of work that ends in a runnable / testable state — small enough that you can stop after any one of them. Status markers:

- `[ ]` not started
- `[x]` done (and verified per its BUILD_PLAN checkpoint)

Steps are sequential. The "go through step N" instruction means: execute every not-yet-done step up to and including step N, then stop.

## Phase 2 — Item reorder via Move to top / bottom

- [ ] **12. Backend: /move endpoint + MoveItemTests** — BUILD_PLAN §4 (Items table /move row), §7.1 `MoveItemTests`, §8 Phase 2 steps 1–2. ## Phase 3 — Simple client-side search

- [ ] **14. Frontend: top-bar search across lists + items** — BUILD_PLAN §8 Phase 3 steps 1–6. Add a search input to the top bar (placeholder "Search lists and items"). On app load, fetch `GET /api/lists` + `GET /api/lists/{id}/items` for every list to build the corpus; refresh the corpus on any mutation. As the user types (debounced 150ms), match list names and item text. Show a dropdown with up to 10 results — each row has a `list` / `item` tag, matched text, and for items a second line `"in <list name>"`. Click list result → activate that list, close dropdown, clear search. Click item result → activate that list, scroll item into view, close dropdown, clear search (no flash, no inline-edit-from-search). Esc clears and closes. Ends at **Checkpoint 3** — search works for lists and items; navigation succeeds; Phase 1 + Phase 2 manual scripts still pass.
